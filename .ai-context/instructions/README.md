# StarkTest — AI agent instructions

Single-module Android app (`:app`) built for the Stark mobile assessment. Read this before making
changes; it captures decisions that aren't obvious from the code alone.

## Architecture

- Single `Activity` (`MainActivity`) + Jetpack Compose. No fragments, no multi-activity nav.
- MVVM. **Exactly one root-level `ViewModel`**: `AppViewModel`, injected only in `StarkApp` (the
  nav root). Feature screens (`features/bikelive`, `features/bikedata`, `features/sessions`,
  `features/userdata`, `features/settings`) are stateless composables — they take plain data + lambda callbacks, never
  a `ViewModel` reference. Keep it that way: if a screen needs new state, add it to `AppUiState`
  and thread it down from `StarkApp`, don't inject a scoped ViewModel into the screen.
- Navigation via Navigation 3 (`androidx.navigation3`). `entry<T> { }` is a member function of the
  `entryProvider { }` lambda receiver, not a top-level import — don't add
  `import androidx.navigation3.runtime.entry`, it doesn't exist.
- Material 3 `adaptive`: compact-only, bottom `NavigationBar` in portrait, `NavigationRail` in
  landscape via `currentWindowAdaptiveInfo().windowSizeClass.windowHeightSizeClass`. No
  multi-pane/list-detail scenes are implemented (out of scope for a compact-only app).
- Koin DI (`di/DataModule.kt`, `di/AppModule.kt`), wired up in `StarkTestApp.onCreate`.
- Typography is Epilogue (`ui/theme/Type.kt`), shipped as two *variable* fonts in `res/font`
  (`epilogue_variable.ttf`, `epilogue_variable_italic.ttf`). Each `FontFamily` entry reuses those
  two files and pins the `wght` axis with `FontVariation.Settings` — don't add a `.ttf` per weight.
  `Typography` remaps every M3 style, so new styles stay on-brand automatically. Resource file
  names must be lowercase/underscore, hence the rename from the vendor's `Epilogue-VariableFont_wght.ttf`.
- Persistence is split by cardinality (`data/local`). Single-valued state — user, bike, battery
  summary, ride settings, diagnostics — lives in a typed
  `DataStore<StarkPreferences>` (`data/local/datastore`, JSON via kotlinx-serialization); a `null`
  field means "never saved". Room holds only `session` (multi-row, autogenerated PK) via
  `SessionDao`. **Do not reintroduce single-row Room tables** — new
  single-valued state goes in `StarkPreferences` as a nullable `@Serializable` DTO with
  `toDomain()`/`from()` mappers, saved with `dataStore.updateData { }`.
- No Retrofit/OkHttp. `NetworkDataSourceImpl` and `BikeTelemetryDataSourceImpl` are fully mocked —
  the former returns a hardcoded `User` after a simulated delay; the latter reads
  `assets/bike_telemetry.json` as a template and derives incrementally-changing values from it,
  emitting one `BikeTelemetry` snapshot every 15 seconds via `Flow` (`TICK_INTERVAL_S`, which also
  drives the simulated elapsed time per tick — keep the two in step).
- Kotlin **explicit backing fields** are enabled via a compiler flag
  (`-XXLanguage:+ExplicitBackingFields` in `app/build.gradle.kts`, not a dedicated CLI flag).
  Inside the declaring class, refer to the property by its own name (not the `field` keyword —
  that's only valid inside get()/set() accessor bodies) to get the wider backing type, e.g.
  `AppViewModel.uiState` is typed `MutableStateFlow` inside the class, `StateFlow` outside it.

## Persistence semantics worth knowing

- `isRiding` (the "simulate riding" toggle in Settings) lives only in `AppUiState` — it is never
  persisted. Don't add a Room column or a `StarkPreferences` field for it.
- `AppDatabase` is at version 2 with `fallbackToDestructiveMigration(dropAllTables = true)`. v1
  held the five single-row tables that DataStore now owns; they were caches of telemetry that
  re-populates on the next tick, so dropping them loses nothing.
- **A ride is one row, written once, and is never persisted while it runs.** The in-progress ride
  *is* the telemetry `Flow` started by `AppViewModel.startTelemetry()`; its running totals live only
  in `AppUiState.liveTelemetry`. `AppViewModel.endRide()` reads the last emitted snapshot before
  `stopTelemetry()` clears it and calls `BikeRepository.saveSession(session)`, which inserts with
  `id = 0` so Room autogenerates. Don't add a per-tick write anywhere: writing to Room per tick is
  what previously left the table with a single perpetually-growing row, and a DataStore copy of the
  active ride was removed as redundant. A ride with `durationS == 0` is dropped rather than saved.
- **The riding toggle going `true` → `false` is the only save path.** There is no lifecycle hook:
  the app does not observe `ON_STOP`, and a process death mid-ride discards it. The app always 
  launches with `isRiding == false`, so there is nothing to recover at startup either.
- `BikeTelemetryDataSource.observeTelemetry()` takes no arguments — every ride starts from zero,
  because a ride never resumes.
- The nav bar contents depend on `isRiding` (`AppDestination.itemsFor`): idle shows BikeData /
  Sessions / User / Settings, riding swaps Sessions for BikeLive. A `LaunchedEffect` in `StarkApp`
  moves off whichever tab the toggle just removed; it also covers process restore, where the back
  stack is saved but `isRiding` (never persisted) is not.

## Testing

- Unit tests only (`app/src/test`) — no instrumented/UI tests are in scope for this assessment.
- Data sources are tested against mocked DAOs/Context (MockK), not an in-memory Room DB. The
  exception is DataStore: `LocalDataSourceImplTest` builds a real file-backed
  `DataStoreFactory.create` over a `TemporaryFolder`, since the JSON round trip is the behaviour
  worth covering and DataStore needs nothing but a writable file on the JVM.
- `AppViewModel` tests use `StandardTestDispatcher` + `Dispatchers.setMain`; advance the scheduler
  with `advanceUntilIdle()` after triggering a suspend call.

## Before committing

Run `./gradlew :app:assembleDebug` and `./gradlew :app:testDebugUnitTest` — both must be green.
